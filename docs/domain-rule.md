# ドメインルール

この文書は友カフェちゃん BOT のゲーム上の契約です。実装を追加・修正する際は、既存コードの都合より優先します。実装済みでない項目は将来の変更で満たすべき要件であり、現状の差異は末尾に記します。

## プレイヤーと登録

- Discord のユーザー ID はプレイヤーを一意に識別する値であり、数値演算してはなりません。保存・比較・API 境界では文字列として扱います。
- プレイヤーは一意に 1 レコードだけ持つ。参加イベント、自動登録、`/register` が競合しても初期報酬は一度だけ付与する。
- 初期登録では設定値の初期豆と初期アイテムを付与する。登録済みプレイヤーの残高・在庫を初期値で上書きしてはならない。
- プレイヤーの戦闘基礎ステータスは `stats`、戦闘中の HP は `Battle` に属する。戦闘で受けたダメージを恒久的な `User.stats` に書き戻さない。

## コーヒー豆（通貨）

- 残高は常に 0 以上の整数である。負の残高を作る更新は禁止する。
- 豆の生成・削除は、デイリー報酬、承認済みの管理者付与、戦闘報酬、購入など、明示されたゲーム操作だけから行う。
- 報酬イベントには一意なイベント ID を持たせ、同じイベントでの加算は 1 回だけにする。戦闘では `battle_id` を用いる。
- 購入は、同じ原子的操作で「十分な残高の確認」「全額減算」「アイテム加算」を行う。失敗時は残高も在庫も一切変化してはならない。
- 購入額はサーバー側の有効な `ItemMaster.market_price` と数量から計算する。クライアント／Discord custom ID から受け取った価格を信用してはならない。
- 管理者の豆付与は対象、数量、実行者、理由、時刻を監査可能にする。数量は正の整数のみとする。

## アイテムとインベントリ

- `ItemMaster.item_id` は不変かつ一意の論理キーである。表示名の変更では ID を変えない。
- 所持数は 0 以上の整数である。消費は `quantity > 0` を条件に原子的に行う。
- 無効化されたマスターは新規の販売・戦闘候補・配布の対象にしない。既に持つアイテムの表示／移行方針は明示する。
- 戦闘アイテムの効果は master の `battle_effect` を正とする。旧配布済み ID の互換表は移行目的に限る。
- 弱点アイテムの推薦は、効果の `target_tags` と戦闘スナップショットのモンスタータグの交差で決める。

## モンスターと戦闘

- 戦闘開始時にモンスターの名前、画像、タグ、メカニクス、能力、報酬を Battle に複製する。途中でマスターを編集しても進行中の戦闘は変化しない。
- 1 プレイヤーにつき進行中 (`active`) の戦闘は最大 1 件とする。DB の部分ユニークインデックスで守る。
- 操作できるのは戦闘を開始した本人だけである。他人のボタン操作は状態変更せず ephemeral に拒否する。
- すべての状態遷移は active、未期限切れ、かつロック取得済みを条件にする。同じボタンの連打・並行操作は 1 回だけ実行する。
- ダメージは最低 1。HP は 0 未満にしない。通常攻撃はプレイヤー攻撃後、敵が生存しているときのみ反撃する。
- `しらべる` は 1 戦 1 回。次回の通常攻撃だけに +3 を適用し、その後必ず消費する。
- 回復／弱点アイテムは 1 個を先に確保・消費し、その後の状態遷移と整合させる。消費できなかったときは戦闘状態を進めない。
- 戦闘は期限切れで `timed_out` になる。期限切れ、取消、勝利、敗北した戦闘を active に戻してはならない。
- 通常プレイヤーの次回挑戦は勝敗後 5 分待機する。管理者用の `!戦闘` は明示的なテスト機能としてこの待機を無視できる。

## 報酬

- 勝利報酬は `battle_id` 単位で最大 1 回だけ付与する。ユーザー側の受領済み ID と戦闘側の `reward_claimed` の両方で冪等にする。
- 報酬の付与後にだけ `reward_claimed` を true にする。障害時の再実行で二重付与しないことを優先する。
- 取消、期限切れ、敗北には勝利豆を付与しない。

## クールダウン

- デイリーは前回受領から 24 時間未満なら拒否し、拒否時に残高と受領時刻を変更しない。
- 戦闘クールダウンは `battle_cooldown_until` が現在より未来の場合のみ開始を拒否する。
- クールダウンの開始・解除はサーバー時刻を基準にし、クライアント時刻を信用しない。

## 権限と管理

- 管理者コマンドは `config.ADMIN_ROLE_NAMES` のいずれかを Discord ギルド内で持つメンバーだけが実行できる。
- 権限の判定はすべての管理入口で同じ認可サービスを通す。Bot のロール認可を Web 管理 API の無認可公開で迂回してはならない。
- 管理データの作成、更新、削除、通貨・アイテム付与は入力検証、認可、監査ログを必要とする。

## 現状との差異

- `User.user_id` は現在 `Number` 定義であり、上記の文字列ルールを満たしていません。
- デイリー、管理付与、ショップ、各種登録は専用の通貨／在庫サービスに集約されていません。
- `shopManager.buyItem` は価格を custom ID から受け取り、単一の原子的更新ではありません。
- Web 管理 API は認証・認可・監査ログをまだ実装していません。
- 戦闘報酬は ID による二重付与防止を実装済みですが、ユーザー更新と Battle の `reward_claimed` 更新は MongoDB トランザクションではありません。障害回復のテストを追加する必要があります。
